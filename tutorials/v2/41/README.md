## 三档任务

- 基础任务：运行 `realtime_probe.exe --ticks 6000 --period-ms 10` 采集 60 秒数据，画出 jitter 直方图和 deadline miss 时间线，解释 P99 延迟与操作系统定时器分辨率的关系，并说明为什么 Windows 下的结果不能作为硬实时保证。
- 岗位挑战：在控制循环中注入一个 5 ms 的模拟计算负载（`std::this_thread::sleep_for` 或密集矩阵运算），分别在默认优先级和 `THREAD_PRIORITY_TIME_CRITICAL` 下测量 jitter 分布变化；再开启第二个线程持续抢占 CPU，对比有/无 CPU 亲和性设置时的 miss 次数。
- 开放探索：把控制循环的生产-消费通信从 `std::mutex` 保护替换为无锁 SPSC 队列（single-producer single-consumer），在相同负载下对比两种方案的 P99 延迟、miss 次数和代码复杂度，先写假设再实验验证。

## 复盘与面试

1. 实时性和吞吐量是一对矛盾：提高控制频率（比如从 100 Hz 提到 1 kHz）时，哪些环节会最先成为瓶颈？你在 jitter 数据中看到的 P99 和最大值之间的差距说明了什么？
2. 在 Windows 上将线程设为 `THREAD_PRIORITY_TIME_CRITICAL` 后 jitter 降低了，但移植到 Linux `SCHED_FIFO` 时行为不同。你会按什么顺序排查定时器分辨率、调度策略、内核抢占配置和 CPU 频率调节（`cpufreq`）的影响？
3. 控制循环和日志线程共享同一个 `std::mutex` 时，最坏情况下的 deadline miss 有多大？无锁队列（SPSC ring buffer）能消除锁竞争，但引入了什么新约束？在什么条件下你会选择无锁方案？
4. 运行 60 秒后出现 3 次 deadline miss，你会按什么顺序排查：操作系统中断、其他进程抢占、内存分配延迟还是控制计算本身超时？如果 miss 集中在某个固定时间间隔，你最怀疑什么根因？
