## 三档任务

- 基础任务：运行 `realtime_probe.exe --ticks 6000 --period-ms 10` 采集 60 秒数据，画出 jitter 直方图和 deadline miss 时间线，解释 P99 延迟与操作系统定时器分辨率的关系，并说明为什么 Windows 下的结果不能作为硬实时保证。
- 岗位挑战：在控制循环中注入一个 5 ms 的模拟计算负载（`std::this_thread::sleep_for` 或密集矩阵运算），分别在默认优先级和 `THREAD_PRIORITY_TIME_CRITICAL` 下测量 jitter 分布变化；再开启第二个线程持续抢占 CPU，对比有/无 CPU 亲和性设置时的 miss 次数。
- 开放探索：把控制循环的生产-消费通信从 `std::mutex` 保护替换为无锁 SPSC 队列（single-producer single-consumer），在相同负载下对比两种方案的 P99 延迟、miss 次数和代码复杂度，先写假设再实验验证。

## 复盘与面试

1. 实时性和吞吐量是一对矛盾：提高控制频率（比如从 100 Hz 提到 1 kHz）时，哪些环节会最先成为瓶颈？你在 jitter 数据中看到的 P99 和最大值之间的差距说明了什么？

<!-- upkie-qa:41-q1 -->
从 100 Hz（周期 10 ms）提到 1 kHz（周期 1 ms），最先成为瓶颈的是操作系统定时器分辨率。本关的实测数据就是直接证据：默认 Windows 定时器分辨率约 15.6 ms，10 ms 周期的 P99 达到 16.283 ms、出现 1717 次 deadline miss——周期比定时器分辨率还短，miss 是必然的；把分辨率调到 1 ms 后，P99 降到 10.283 ms、最大 11.321 ms、零 miss，说明瓶颈确实来自定时器粒度。第二个瓶颈是计算本身：1 ms 周期里控制律计算、状态估计、通信必须全部完成，任何一次内存分配（`malloc` 触发页错误）或缓存未命中都可能吃掉几百微秒。第三个瓶颈是中断：USB、网卡、磁盘中断会抢占用户线程，频率越高被中断打断的概率越大。P99 和最大值的差距（本关数据：P99 10.283 ms vs 最大 11.321 ms，差距约 1 ms）说明偶发扰动的幅度——P99 代表"绝大多数时候"，最大值代表"最坏一次"，两者差距越小说明系统越稳定；如果最大值是 P99 的三倍，说明有周期性的大扰动（比如某个后台服务每隔几秒做一次磁盘写入）。面试时的判断框架：先看 P99 是否满足周期要求，再看最大值是否会导致失稳，两者都要报告，不能只看平均值。常见误区是"平均延迟满足要求就行"——本关正文明确说"平均能跑不等于最坏情况安全"，控制环的稳定性由最坏情况决定。
<!-- /upkie-qa -->

2. 在 Windows 上将线程设为 `THREAD_PRIORITY_TIME_CRITICAL` 后 jitter 降低了，但移植到 Linux `SCHED_FIFO` 时行为不同。你会按什么顺序排查定时器分辨率、调度策略、内核抢占配置和 CPU 频率调节（`cpufreq`）的影响？

<!-- upkie-qa:41-q2 -->
排查顺序从"最容易验证且影响最大"开始。第一步查定时器分辨率：Windows 的 `THREAD_PRIORITY_TIME_CRITICAL` 隐式把定时器分辨率提到 1 ms（本关用 `ctypes.windll.winmm` 显式做这件事），Linux 的 `SCHED_FIFO` 不会自动改定时器分辨率，需要单独调用 `clock_nanosleep` 或确认 `CONFIG_HIGH_RES_TIMERS=y`——如果 Linux 上还在用低分辨率的 `sleep`，jitter 自然比 Windows 大。第二步查调度策略：`SCHED_FIFO` 是实时调度类，优先级 1~99，必须用 `sched_setscheduler` 显式设置，普通 `nice` 值对实时线程无效；如果线程实际跑在 `SCHED_OTHER`（默认），任何普通进程都能抢占它。第三步查内核抢占配置：`CONFIG_PREEMPT_RT` 补丁把 Linux 内核变成完全可抢占，没有这个补丁时，内核临界区（比如中断处理、自旋锁）会阻塞实时线程，产生几十微秒到几毫秒的不可预测延迟——用 `cyclictest -p 99 -t -n` 可以直接测量。第四步查 `cpufreq`：CPU 频率调节器如果是 `ondemand` 或 `powersave`，空闲时降频，控制线程唤醒后需要几毫秒才能升回全速，这段升频时间直接计入 jitter；改成 `performance` 模式锁定最高频率可以消除这个扰动。面试时的判断框架：Windows 和 Linux 实时行为差异的根源是"Windows 隐式做了很多事（定时器分辨率），Linux 需要显式配置每一步"。常见误区是在 Linux 上只设了 `SCHED_FIFO` 就以为够了，实际上四步都要做。
<!-- /upkie-qa -->

3. 控制循环和日志线程共享同一个 `std::mutex` 时，最坏情况下的 deadline miss 有多大？无锁队列（SPSC ring buffer）能消除锁竞争，但引入了什么新约束？在什么条件下你会选择无锁方案？

<!-- upkie-qa:41-q3 -->
最坏情况下的 deadline miss = 日志线程持锁的最长时间。如果日志线程在持锁期间做了一次磁盘写入（`fwrite` 触发系统调用），Windows 上文件 I/O 可能阻塞几十毫秒，控制线程在这期间完全无法获取状态，直接 miss 若干个周期。本关的岗位挑战要求注入 5 ms 模拟负载来测量这类影响——5 ms 的持锁时间对 10 ms 周期意味着 50% 的时间控制线程被阻塞，P99 会急剧恶化。SPSC（single-producer single-consumer）无锁 ring buffer 消除了锁竞争，控制线程写、日志线程读，两者永远不阻塞对方。但它引入三个新约束：一是容量固定，缓冲区满了生产者必须丢弃数据或自旋等待，需要设计好溢出策略（控制环里通常丢弃最旧的帧）；二是严格单生产者单消费者，一旦有两个线程同时写就会数据损坏，代码结构必须保证这一点；三是内存序（memory ordering）必须正确，`std::memory_order_acquire/release` 用错了在 x86 上可能碰巧正确，移植到 ARM 就会出错。选择无锁方案的条件：控制周期短（≤1 ms）、锁竞争导致的 miss 已经被实测数据证实是主要瓶颈、团队有能力正确实现内存序。面试时的判断框架：先用 `std::mutex` 做基线，测量 miss 次数，如果 miss 主要来自锁竞争再考虑无锁；不要在没有测量数据的情况下预先优化。常见误区是"无锁一定更快"——无锁的 CAS 操作在高竞争下会自旋重试，比锁更慢；SPSC 无锁只在单生产者单消费者且低竞争时才有优势。
<!-- /upkie-qa -->

4. 运行 60 秒后出现 3 次 deadline miss，你会按什么顺序排查：操作系统中断、其他进程抢占、内存分配延迟还是控制计算本身超时？如果 miss 集中在某个固定时间间隔，你最怀疑什么根因？

<!-- upkie-qa:41-q4 -->
排查顺序：先看 miss 的时间分布，再决定查什么。本关的 60 秒采集（6000 个周期样本）里，默认定时器出现 1717 次 miss 是系统性的（定时器分辨率问题），而高分辨率定时器下零 miss——如果 3 次 miss 是随机散布的，最可能是操作系统中断（USB 轮询、网卡中断、时钟中断），用 Windows 的 `xperf` 或 Linux 的 `perf record -e irq:irq_handler_entry` 可以直接看到中断发生时刻和持续时间。如果 miss 集中在某个固定时间间隔（比如每隔 30 秒一次），最怀疑周期性后台任务：Windows 的磁盘碎片整理、防病毒扫描、Windows Update 检查，Linux 的 `cron` 任务、`systemd-journald` 刷盘、`logrotate`——这类任务每隔固定时间触发一次，持续几十毫秒，正好对应固定间隔的 miss。其他进程抢占：用任务管理器或 `top` 看 miss 时刻是否有 CPU 占用尖峰。内存分配延迟：控制循环里不应该有任何动态内存分配（`new`/`malloc`），如果有，第一次分配可能触发页错误，耗时几毫秒；排查方法是在控制循环外预分配所有缓冲区。控制计算本身超时：本关的控制律是四状态点积，计算量极小（纳秒级），不可能是根因，除非有人不小心在循环里加了矩阵求逆。面试时的判断框架：固定间隔 → 周期性后台任务；随机散布 → 中断；启动后前几次 → 内存分配/缓存预热。常见误区是一上来就怀疑自己的代码，实际上 60 秒 3 次 miss（0.05%）在通用操作系统上是正常背景噪声，关键是确认它不是系统性的。
<!-- /upkie-qa -->
