## 复盘与面试

1. 本关最关键的假设是什么？失效时第一个可观测信号是什么？

<!-- upkie-qa:H09-q1 -->
最关键的假设是：遥测数据的有效性可以用 `valid = sequence_new AND timestamp_fresh AND value_bounded` 三个条件的逻辑与来判定——即一帧遥测数据只有在序号严格递增（没有重放或乱序）、时间戳在新鲜度窗口内（没有过期数据）、数值在物理合理范围内（没有传感器故障或通信错误）时，才能被控制系统使用。这个假设的本质是"不可信的数据比没有数据更危险"：一帧时间戳过期的姿态数据会让控制器用旧状态计算力矩，一帧数值越界的力矩反馈会让安全链误判执行器状态。假设失效时（比如 WebSocket 连接断开后重连，序号重置导致 sequence_new 判断失效），第一个可观测信号是 `valid=False` 的帧数突然增加，或者更危险的情况：`valid=True` 但实际上数据已经过期（timestamp_fresh 的阈值设置过宽）。本关正文的遥测契约（`src/upkie_mujoco_course/hardware/telemetry.py`）明确规定"任何时间倒退、非有限数值或维度错误都必须在数据入口拒绝"——这是假设失效时的最后一道防线：与其让坏数据进入控制环，不如在入口处直接丢弃。需要注意的是，本关当前建设状态为"规划中"，`course_checkpoint.py --chapter H09` 会明确拒绝验收。面试时的判断框架：遥测数据验证的三个条件对应三类故障——序号对应通信乱序/重放，时间戳对应延迟/断流，数值范围对应传感器故障；三者缺一不可，少任何一个都会让某类故障漏过验证。常见误区是"只检查数值范围就够了"——数值在合理范围内的过期数据（比如 5 秒前的姿态）对控制环同样危险，timestamp_fresh 检查是不可省略的。
<!-- /upkie-qa -->

2. 为什么当前接口、单位和限幅这样设计？有哪些可替代方案？

<!-- upkie-qa:H09-q2 -->
遥测契约的字段设计覆盖了控制系统的完整状态快照：严格递增的序号和时间（通信完整性）、`proprioception`（本体感觉，与第 36 章 BC 策略的输入格式一致）、6 维 `action`（与第 35 章的高层动作契约 `[forward_velocity, yaw_rate, stop, 0, 0, 0]` 一致）、左右轮力矩与电流（执行器状态，与第 38 章的力矩接口 N·m 一致）、电池电压（供电状态，H03 章）、急停和故障码（安全状态，H08 章的 estop 和第 43 章的 safety_flag）。所有物理量使用 SI 单位（N·m、A、V、rad、rad/s），与课程软件部分保持单位一致，避免遥测数据和控制指令之间的单位换算错误。`valid` 的三个限幅条件：sequence_new 要求序号严格递增（相等或倒退都无效），timestamp_fresh 要求时间戳在新鲜度窗口内（比如 <50 ms，对应 20 Hz 遥测率的 1 个周期），value_bounded 要求每个字段在物理合理范围内（比如力矩 ±1.0 N·m、电池电压 6~12.6 V）。替代方案：用 CRC 校验代替序号检查（能检测通信位错误，但不能检测重放攻击或乱序）；或者用发布-订阅中间件（如 ROS2 话题）代替 WebSocket（有内置的 QoS 机制，但引入额外依赖，不适合资源受限的嵌入式平台）。需要注意的是，本关当前为规划中状态，具体的新鲜度窗口和数值范围尚未确定。面试时的判断框架：遥测接口设计的核心问题是"这帧数据能不能被信任"，三个验证条件分别回答"是不是新的""是不是及时的""是不是合理的"，三者共同构成信任判据。常见误区是"WebSocket 连接正常就等于数据正常"——连接正常只说明通信链路存在，不能保证数据内容正确，value_bounded 检查是不可省略的最后一道防线。
<!-- /upkie-qa -->

3. 你能用哪三份证据证明结果可复现？

<!-- upkie-qa:H09-q3 -->
遥测系统的可复现性证据需要覆盖"数据完整性、验证逻辑、边界行为"三个层次。第一份是数据完整性记录：在固定时长（比如 60 秒）的正常运行中，统计总帧数、有效帧数（valid=True）、各类无效帧数（序号错误/时间戳过期/数值越界各多少），计算有效帧率；这是遥测链路健康状态的基线证据，让别人能在相同网络条件下重测得到相近的有效帧率。第二份是验证逻辑记录：故意注入三类故障帧（序号倒退帧、时间戳过期帧、数值越界帧），确认每类故障帧都被 `valid=False` 正确拒绝，且拒绝后控制系统进入安全降级（使用上一帧有效数据或进入安全停止）；这是验证逻辑正确性的证据，与第 42 章日志契约的"失效字段拒绝机制"设计原则一致。第三份是边界行为记录：WebSocket 断开重连后的序号恢复行为（重连后序号是否从断点继续，还是重置）、网络延迟增大时 timestamp_fresh 的触发频率（延迟超过新鲜度窗口后，有效帧率如何下降）、电池电压接近下限时 value_bounded 的触发行为；这是边界条件下的系统行为证据。三份证据的分工：完整性记录回答"正常时数据质量怎么样"，验证记录回答"坏数据能不能被拒绝"，边界记录回答"极端情况下系统怎么降级"。需要注意的是，本关当前为规划中状态，这三份证据的具体格式和验收标准尚未建立。面试时的判断框架：遥测证据的可复现性依赖固定的网络条件——WiFi 信号强度、干扰源距离都会影响有效帧率，不记录网络条件的遥测数据没有可比性。常见误区是"只测正常工况的有效帧率"——遥测系统的价值在故障工况，正常工况下所有通信协议都表现良好。
<!-- /upkie-qa -->

4. 如果指标退化 20%，你先查模型、数据、控制还是部署？为什么？

<!-- upkie-qa:H09-q4 -->
先查部署，在遥测语境下对应的是"网络环境和通信链路"。如果有效帧率退化 20%（比如从 99% 降到 79%），最可能的根因是网络层面的变化，而不是遥测协议本身——`valid = sequence_new AND timestamp_fresh AND value_bounded` 的验证逻辑一旦写好不会自己退化。排查顺序：第一步确定是哪类无效帧增加了（序号错误 → 通信乱序或重连问题；时间戳过期 → 网络延迟增大；数值越界 → 传感器或执行器问题）——这三类的根因完全不同，必须先分类再排查；第二步查网络环境（WiFi 信道是否拥挤、路由器是否重启、机器人是否移动到了信号弱的区域——网络延迟增大是 timestamp_fresh 失败的最常见原因）；第三步查 WebSocket 连接状态（是否有频繁断线重连，重连后序号是否正确恢复）。模型和数据完全不相关——遥测验证是确定性逻辑，不涉及任何训练模型；控制律也不会影响遥测数据的有效性（控制律影响的是 action 字段的值，但 value_bounded 检查的是值是否在物理范围内，控制律正常时 action 不会越界）。本关正文的"先低能量验证，再逐级闭环"在这里的排查体现是：先在静态环境下（机器人不动、网络稳定）重测有效帧率，确认退化是否可复现；如果静态时正常但运行时退化，说明问题来自机器人运动引起的网络变化（比如天线方向改变、电机 PWM 干扰 WiFi）。面试时的判断框架：遥测退化的排查顺序是"分类无效帧 → 查网络 → 查连接 → 查传感器"，从最可能到最不可能；先分类再排查，不要一上来就换路由器。常见误区是"有效帧率低就提高发送频率"——如果根因是网络延迟，提高发送频率只会让缓冲区更快溢出，有效帧率反而更低。
<!-- /upkie-qa -->
