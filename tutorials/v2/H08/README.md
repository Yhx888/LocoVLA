## 复盘与面试

1. 本关最关键的假设是什么？失效时第一个可观测信号是什么？

<!-- upkie-qa:H08-q1 -->
最关键的假设是：安全滤波链 `tau_safe = estop · rate_limit(low_pass(tau_raw))` 的每一级都能独立生效，且级联顺序是正确的——即急停信号（estop，0 或 1）可以在任何时刻把输出力矩强制归零，不受 rate_limit 和 low_pass 状态的影响。这个假设的本质是"安全机制的优先级高于控制性能"：estop 是乘法门控（estop=0 时 tau_safe 恒为 0），rate_limit 限制力矩变化速率（防止执行器冲击），low_pass 滤除高频噪声（防止传感器噪声引起执行器抖动）。假设失效时，第一个可观测信号取决于哪一级出了问题：如果 estop 信号没有正确传播（比如急停按钮接线松动），按下急停后 tau_safe 不归零，这是最危险的失效模式；如果 rate_limit 的限幅值设置过大，力矩阶跃变化没有被有效限制，执行器在急停后的制动过程中可能产生机械冲击；如果 low_pass 的截止频率过低，控制带宽被压缩，平衡控制的响应变慢，机器人"软"——推一下晃很久才恢复。本关正文的"先低能量验证，再逐级闭环"在这里的体现是：先验证 estop 功能（按下急停，确认力矩立即归零），再验证 rate_limit（施加阶跃指令，确认力矩变化速率在限制内），最后才验证闭环平衡性能。需要注意的是，本关当前建设状态为"规划中"，`course_checkpoint.py --chapter H08` 会明确拒绝验收。面试时的判断框架：安全链的验证顺序必须从最高优先级开始（estop → rate_limit → low_pass），如果最高优先级失效，后面的验证都没有意义。常见误区是"先调控制性能再测安全"——安全功能必须在控制闭环之前就验证通过，不能"等机器人跑起来了再测急停"。
<!-- /upkie-qa -->

2. 为什么当前接口、单位和限幅这样设计？有哪些可替代方案？

<!-- upkie-qa:H08-q2 -->
`tau_safe = estop · rate_limit(low_pass(tau_raw))` 的级联顺序是刻意的：low_pass 在最内层（先滤波，去除传感器噪声引起的力矩毛刺），rate_limit 在中间（限制滤波后力矩的变化速率，防止执行器冲击），estop 在最外层（乘法门控，任何时候都能把最终输出归零）。这个顺序保证了 estop 的响应延迟为 0——不需要等 low_pass 的滤波器状态衰减，也不需要等 rate_limit 把力矩斜坡降下来，estop=0 直接让 tau_safe=0。tau_raw 和 tau_safe 的单位都是 N·m（与第 38 章的力矩接口一致），rate_limit 的单位是 N·m/s（力矩变化速率上限），low_pass 的截止频率单位是 Hz 或 rad/s。限幅设计：rate_limit 的值取决于执行器的机械承受能力（比如最大 10 N·m/s，意味着从 0 到满力矩需要 0.1 s），estop 是硬性的 0/1 门控没有中间状态。本关正文要求"所有物理量使用 SI 单位"，采样周期 dt 必须明确说明（rate_limit 的离散实现依赖 dt：`delta_tau_max = rate_limit * dt`）。替代方案：把 estop 放在 rate_limit 之前（先切断输入，再让 rate_limit 把残余力矩斜坡降下来），这样急停后力矩不是立即归零而是按斜坡下降，对机械更温和，但急停响应时间变长；或者用硬件急停（直接切断电机供电）代替软件门控，响应更快但失去了"受控制动"的能力（电机自由滑行而不是主动制动）。需要注意的是，本关当前为规划中状态，具体的 rate_limit 值和 low_pass 截止频率尚未确定。面试时的判断框架：安全链设计的核心权衡是"响应速度 vs 机械温和"，急停场景优先响应速度，正常停机场景可以优先机械温和。常见误区是"low_pass 截止频率越低越安全"——截止频率太低会引入相位滞后，让平衡控制不稳定，安全滤波不能以牺牲控制稳定性为代价。
<!-- /upkie-qa -->

3. 你能用哪三份证据证明结果可复现？

<!-- upkie-qa:H08-q3 -->
实机 LQR 和安全链的可复现性证据需要覆盖"安全功能、控制性能、边界行为"三个层次。第一份是安全功能记录：急停响应时间（从按下急停按钮到 tau_safe 归零的时间，应该 <1 ms，即同一个控制周期内完成）、rate_limit 触发时的力矩变化速率（应该不超过设定值）、estop 后恢复流程（必须经过明确的人工复位，不能自动恢复）；这是安全链有效性的直接证据，与第 43 章安全状态机的"FAULT 只能人工复位"设计原则一致。第二份是控制性能记录：LQR 闭环的阶跃响应（施加已知扰动后，俯仰角恢复到平衡位置的时间、超调量、稳态误差），在固定负载和固定供电电压下测量；这是控制律性能的量化证据，让别人能在相同条件下重测得到相近的动态响应。第三份是边界行为记录：rate_limit 饱和时的控制性能退化（大扰动下力矩被限速，恢复时间变长）、low_pass 截止频率附近的相位滞后（在截止频率附近的扰动，控制响应出现明显延迟）、estop 在高速运行时的制动距离（从全速到完全停止的时间和位移）；这是安全边界内的性能极限证据。三份证据的分工：安全记录回答"保护功能有没有"，性能记录回答"正常控制好不好"，边界记录回答"极限情况下会怎样"。需要注意的是，本关当前为规划中状态，这三份证据的具体格式和验收标准尚未建立。面试时的判断框架：实机控制证据的可复现性依赖固定的机械状态和供电条件——同一台机器人在电池满电和半电下的 LQR 响应可能完全不同，不记录供电电压的性能数据没有可比性。常见误区是"只测正常工况"——安全系统的价值在边界工况，正常工况下所有系统都表现良好。
<!-- /upkie-qa -->

4. 如果指标退化 20%，你先查模型、数据、控制还是部署？为什么？

<!-- upkie-qa:H08-q4 -->
先查部署，在实机控制语境下对应的是"传感器、执行器和供电"。如果 LQR 闭环的恢复时间退化 20%（比如从 0.5 s 增大到 0.6 s），最可能的根因是硬件层面的变化，而不是 LQR 增益矩阵——LQR 增益一旦计算好不会自己变化，除非有人改了代码或配置。排查顺序：第一步查 IMU（H06 章的姿态估计——如果陀螺仪偏置增大或加速度计噪声增大，theta_k 的质量下降，LQR 的状态反馈出现误差，控制性能自然退化；这是最常见的根因，因为 IMU 对温度和振动敏感）；第二步查执行器（H04/H07 章的电机和舵机——如果电机 Kt 因温度下降、或舵机齿轮磨损，同样的控制指令产生的实际力矩变小，等效于控制增益降低，恢复时间变长）；第三步查供电（电池电压下降——电机力矩与供电电压相关，电压降低 20% 会让最大可用力矩降低约 20%，LQR 在大扰动下更容易触及 rate_limit，恢复时间变长）。LQR 增益是最后才查的，因为增益矩阵是从系统模型（质量、惯量、电机参数）计算出来的，只有物理参数变了才需要重新计算。本关正文的"先低能量验证，再逐级闭环"在这里的排查体现是：先开环测试（给固定力矩指令，测量实际加速度），确认执行器本身正常；如果开环正常但闭环退化，说明问题在传感器反馈（IMU），而不是执行器。面试时的判断框架：实机控制退化的排查顺序是"传感器 → 执行器 → 供电 → 控制参数"，与仿真正好相反——仿真里参数是精确的，实机里参数会漂移。常见误区是"性能退化就重新调 LQR 增益"——如果根因是 IMU 漂移，重新调增益只是在错误的传感器数据上拟合，传感器问题不解决，增益调多少次都会再退化。
<!-- /upkie-qa -->
