# H01 复刻范围、许可证与 BOM 审计

> 建设状态：可执行  
> 阶段：硬件选修（独立于毕业项目）  
> 作品集目录：`outputs/portfolio/H01`

## 岗位任务

在采购、加工或复刻一个开源轮足项目之前，先回答三件事：资产能否合法参考，BOM 是否足以实际下单，资料缺口会不会直接转化为供电、装配或安全风险。本关以 [Micro-Wheeled_leg-Robot](https://github.com/MuShibo/Micro-Wheeled_leg-Robot) 为只读审计对象，不复制 CAD、PCB 或授权不明确的资产。

本关的“通过”表示审计脚本能够把不充分证据识别出来并冻结采购；它绝不表示该仓库已获得统一授权，也不表示机器人可以上电。

## 学习目标

- 区分仓库根许可证、单文件许可头、README 描述和可采购 BOM 的法律与工程含义。
- 用固定 commit 而非浮动分支名保存审计证据。
- 将每个 BOM 条目标记为“README 已提及”“README 未提及”或“实际目录未找到”。
- 在型号、数量、供应商、接口或许可缺失时做出可复核的采购冻结结论。

## 前置关卡

这是高级选修的起点，不依赖 `47` 毕业项目。实机经验者可跳过基础电子知识，但不能跳过许可、供电和采购边界审计。

## 先观察现象

```powershell
python scripts/run_hardware_audit.py --chapter H01
```

本次真实远程快照锁定为 commit `19a012ec8ee8b4f981aab887409a64b8dff37725`，默认分支为 `master`。审计发现根目录没有 `LICENSE`、`COPYING` 或 `NOTICE`；README 覆盖 7 个候选 BOM 项中的 6 个，源码抽样 3 个文件的 MIT 文件头比例为 `0.0`。因此采购冻结，不能将历史印象或单个文件的旧许可说法当作当前证据。

## 直觉与概念

<!-- upkie-animation:h01-core -->

README 像一张愿望清单，BOM 像可下单的工程合同，许可证则限定你能如何使用资料。三者不是同一件事。一个“ESP32”字样没有型号、数量、接口电平、供应商和替代料，就不能让采购人员安全下单；一个源码文件出现许可头，也不能自动授权同仓库中的 CAD 或 PCB。

## 教科书级展开

审计对象可写为：

审计结论 = commit + 根许可证 + 源码许可抽样 + BOM 证据 + 采购风险

其中 commit 是不可变的 Git 标识，不带物理单位；BOM 的数量单位是 `pcs`，价格应是货币/pcs，电池电压是 `V`，电流是 `A`。本关没有假设“缺少许可证就一定侵权”，它只说明授权范围不明确，课程只能链接原仓库而不能复制未明确资产。失效条件包括仓库后续更新、GitHub API 不可用、README 改写或审计样本不足；任一情况都必须重新锁定 revision。

`fetch_repository_snapshot()` 依次读取仓库元数据、分支 commit、递归文件树、README 和三个源码文件头。`audit_repository_snapshot()` 查找根许可证名、计算源码 MIT 头比例，并将 PCB、ESP32、L6234PD013TR、AS5600、MPU6050、舵机、GH1.25 写成差异表。代码不会下载或导入 CAD/PCB，只记录路径和文本证据。

本次指标为：根许可证缺失 `1.0`、BOM 项数 `7.0`、采购冻结 `1.0`。README 覆盖率约为 `0.8571428571428571`，但这不是 BOM 完整率，因为实际下单字段仍然缺失。将 `0.857` 写成“85.7% 可以采购”是错误推论。

## 故障诊断挑战

故意把 `root_license_present=False` 改成 `True`，但保持根目录文件树不变。现象是采购冻结会被错误放宽；第一处异常证据是日志中的许可证字段与 `root_paths` 矛盾。最小修复是恢复从文件树计算许可证，而不是手工填布尔值。

另一个常见错误是把 README 中的“舵机”同义词或图片说明误当成精确型号。应记录原始文本、型号、数量、连接器、供电电压和证据 URL；缺一项即保留冻结。

## 三档任务

- 基础任务：复现快照并解释三个通过条件为何都指向“停止采购”。
- 岗位挑战：为每个 BOM 项补充型号、数量、替代料、单价、供应风险和证据链接，再重新审计。
- 开放探索：若项目作者补充根许可证，先复核授权覆盖的资产类别，再决定是否解除哪一部分冻结；不要把软件许可外推到 CAD/PCB。

## 复盘与面试

1. 为什么固定 commit 比默认分支更适合审计？

<!-- upkie-qa:H01-q1 -->
默认分支（本关审计对象的 `master`）是浮动的：仓库作者随时可以推送新提交，改变 README 内容、添加或删除文件、甚至修改许可证。如果你用"master 分支"作为审计依据，今天审计通过的结论明天可能就不成立了——审计证据失去了可复现性。固定 commit（本关锁定的 `19a012ec8ee8b4f981aab887409a64b8dff37725`）是不可变的 Git 标识：这个 commit 对应的文件树、README 文本、源码内容永远不会改变，任何人任何时候 checkout 这个 commit 都能看到完全相同的审计对象。本关正文明确列出了失效条件："仓库后续更新、GitHub API 不可用、README 改写或审计样本不足；任一情况都必须重新锁定 revision"——这正是固定 commit 的价值所在：它把"审计时的仓库状态"冻结成一个可引用的快照，而不是一个会漂移的目标。工程上的类比：固定 commit 之于代码审计，就像固定 seed 之于随机实验（第 25~31 章的 RL 训练全部要求固定 seed），两者都是为了把"这次运行的结果"变成可复现的证据。面试时的判断框架：任何审计、测试或实验，如果输入是可变的，结论就是不可信的；固定输入是证据链的第一环。常见误区是"分支名就够了"——`master` 在审计期间被 force push 的案例并不罕见，用分支名作为证据等于把审计结论建立在别人的善意上。
<!-- /upkie-qa -->

2. 根许可证缺失和单文件许可头分别意味着什么？

<!-- upkie-qa:H01-q2 -->
两者是完全不同的法律信号，不能互相替代。根许可证（仓库根目录的 `LICENSE`、`COPYING` 或 `NOTICE` 文件）声明的是整个仓库的统一授权条款：它告诉所有人"这个仓库里的所有内容，在这些条件下可以使用"。本关审计发现根目录没有这三个文件中的任何一个，`root_license_present=False`——这意味着整个仓库没有统一的授权声明，默认情况下所有资产（代码、CAD、PCB 设计）都处于"保留所有权利"状态，未经作者明确授权不能复制、修改或分发。单文件许可头（源码文件顶部的 SPDX 标识或许可文本）只覆盖那一个文件：本关抽样 3 个源码文件，MIT 文件头比例为 0.0，即连单个文件都没有明确的许可声明。即使某些文件有 MIT 头，也不能自动授权同仓库中的 CAD 或 PCB——本关正文明确指出"一个源码文件出现许可头，也不能自动授权同仓库中的 CAD 或 PCB"。两者的工程含义：根许可证缺失 → 整个仓库的资产使用范围不明确 → 采购冻结；单文件许可头 → 只能证明那个文件本身可能有某种授权，不能外推。面试时的判断框架：许可证审计的优先级是"根许可证 > 子目录许可证 > 单文件头"，任何下位证据都不能覆盖上位缺失。常见误区是"看到某个文件有 MIT 头就以为整个仓库是 MIT"——这是本关故障诊断挑战里描述的错误：把 `root_license_present=False` 手工改成 `True` 会错误放宽采购冻结。
<!-- /upkie-qa -->

3. README 覆盖率为什么不能替代 BOM 完整率？

<!-- upkie-qa:H01-q3 -->
本关的数据直接说明了这个区别：README 覆盖率约 0.857（7 个候选 BOM 项中 README 提及了 6 个），但采购仍然冻结——因为 README 提及一个元件和这个元件可以被实际下单是完全不同的两件事。本关正文的类比很精准："README 像一张愿望清单，BOM 像可下单的工程合同。"README 里写"ESP32"只是提到了这个名字，但采购人员需要的是：具体型号（ESP32-WROOM-32 还是 ESP32-S3？）、数量（每块板需要几个？）、接口电平（3.3V 还是 5V 逻辑？）、供应商（哪家有货？）、替代料（缺货时用什么替换？）。本关的 BOM 差异表把每个条目标记为"README 已提及""README 未提及"或"实际目录未找到"，但这三个标记都不是"可以下单"——即使 README 提及了，只要型号、数量、供应商、接口或许可中任何一项缺失，该条目就不能让采购人员安全下单。本关正文明确警告："将 0.857 写成'85.7% 可以采购'是错误推论。"面试时的判断框架：覆盖率回答"提到了什么"，完整率回答"能否实际执行"，两者之间的差距就是"愿望"和"合同"的差距。常见误区是把 README 当成工程文档——README 的读者是"想了解这个项目的人"，BOM 的读者是"要实际采购和装配的人"，两者的信息需求完全不同。
<!-- /upkie-qa -->

4. 采购冻结如何保护后续 FOC、IMU 和上电安全工作？

<!-- upkie-qa:H01-q4 -->
采购冻结的本质是"在授权和规格不明确时，阻止后续工作建立在不可靠的基础上"。本关审计的 BOM 条目包括 L6234PD013TR（三相电机驱动，FOC 控制的核心）、AS5600（磁编码器，FOC 换向的反馈来源）、MPU6050（IMU，姿态估计的传感器）——这三个元件的型号、接口电平和供电规格如果不确定，后续的 FOC 调试、IMU 校准和上电序列都是在赌"买到的东西和预期一样"。具体风险：如果 L6234PD013TR 的驱动电压和电流规格没有确认（本关 BOM 差异表里这些字段缺失），上电时可能因为供电不匹配烧毁驱动芯片，或者因为 PWM 频率超出芯片能力导致电机失控；如果 AS5600 的接口电平（I2C 地址、上拉电阻值）没有确认，FOC 换向角度可能读取错误，电机反转或振荡；如果 MPU6050 的供电电压（3.3V 还是 5V）没有确认，IMU 可能损坏或输出漂移，姿态估计失效导致平衡控制崩溃。采购冻结强制在这些问题被回答之前停止采购，把风险从"上电时爆炸"前移到"审计时发现问题"。本关正文的定位很准确："本关的'通过'表示审计脚本能够把不充分证据识别出来并冻结采购；它绝不表示该仓库已获得统一授权，也不表示机器人可以上电。"面试时的判断框架：硬件安全的成本曲线是"越早发现问题修复成本越低"，审计阶段发现规格缺失的成本是零，上电后发现芯片烧毁的成本是时间、金钱和可能的安全事故。常见误区是"先买回来再说"——硬件调试里最昂贵的错误都是在规格不明确时发生的。
<!-- /upkie-qa -->
