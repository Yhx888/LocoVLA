## 先观察现象

**错误基线实验**：只在训练分布内的场景中评估策略。

```python
# 只在"正前方红色目标"上测试（与训练数据相同）
for ep in range(20):
    success = evaluate("前往红色目标并停车", target_pos=[1.0, 0.0])
    results.append(success)

mean_success = np.mean(results)
print(f"分布内成功率: {mean_success:.0%}")
# 预期: 90%+ (因为训练数据覆盖了这个场景)
```

**然后**：在训练分布外的场景测试。

```python
# "蓝色目标"（训练中可能覆盖不足）
success_ood = evaluate("前往蓝色目标并停车", target_pos=[-1.0, 0.0])
print(f"分布外成功率: {success_ood:.0%}")
# 预期: 大幅下降（可能 < 30%）
```

**记录观察**：分布内性能好不代表分布外也好——这就是泛化问题。

## 直觉与概念

<!-- upkie-animation:37-intuition -->

### 泛化的三个层次

**1. 数据泛化**：在新的随机种子下表现好（同一场景，不同扰动）

训练: 红色目标在 (1.0, 0.1), seed=42
测试: 红色目标在 (1.0, 0.1), seed=99  ← 不同扰动

**2. 场景泛化**：在训练时没见过的场景配置下表现好

训练: 红色目标在 (1.0, 0.0) 和 (0.5, 0.5)
测试: 红色目标在 (0.7, 0.3)  ← 新的位置组合

**3. 条件泛化**：在训练时没见过的物理条件下表现好

训练: 标准质量、标准摩擦
测试: 质量 +30%、摩擦 -50%  ← 物理参数变化

每个层次比前一个更难。好的系统应该在层次 1 和 2 上表现良好，在层次 3 上至少不崩溃（安全降级）。

### 失败模式分类

| 失败模式 | 触发条件 | 第一个信号 | 严重度 |
|---|---|---|---|
| 感知失败 | 目标颜色在训练分布外 | 检测结果为空 | 中（策略原地等待） |
| 分布偏移 | 初始状态远离训练分布 | 动作异常大或异常小 | 高（可能导致翻倒） |
| 累积误差 | 长时间运行 | 轨迹逐渐偏离 | 中（最终可能迷路） |
| 指令歧义 | 模糊或矛盾的指令 | 策略犹豫（动作频繁切换） | 低（安全层兜底） |
| 执行器饱和 | 需要大力矩恢复 | ctrl 频繁触碰限幅 | 高（可能失去平衡） |

### 运行时安全监控

实际项目通过 `VLASafetyController` 的内置计数器实现运行时监控：

```python
# VLASafetyController 已内置安全干预计数
controller = VLASafetyController()

# 运行结束后检查
print(f"安全干预次数: {controller.safety_interventions}")
print(f"总步数: {total_steps}")
print(f"干预率: {controller.safety_interventions / total_steps:.1%}")
```

`VLASafetyController.safety_interventions` 记录了运行中因俯仰角超限而被拦截的次数。如果干预率过高（如 > 20%），说明策略频繁输出不安全的速度指令，需要改进训练数据或调整安全阈值。

## 故障诊断挑战

<!-- upkie-animation:37-comparison -->

**破坏**：在 `VLASafetyController` 中去掉俯仰角安全检查——把 `soft_pitch_limit` 设为无穷大，使安全层永远不干预。

**第一处异常**：当策略输出较大的速度指令时，机器人躯干大幅倾斜，但因为没有安全层拦截，系统继续执行。机器人可能在几步内失去平衡倒下——而之前安全层会在俯仰角超过 0.18 rad 时提前将速度置零。

**根因假设**：安全检查是"早期保护"。去掉它意味着系统只能依赖底层平衡控制器的固有能力，一旦速度指令超出平衡能力范围就无法恢复。

**最小修复**：恢复 `soft_pitch_limit=0.18` 的安全检查。

**验证**：在所有任务中，`safety_interventions` 计数 > 0（说明安全层发挥了作用），且机器人不会倒下。

## 复盘与面试

1. 三种泛化层次的区别？

<!-- upkie-qa:37-q1 -->
本关正文把泛化分成三个递进层次，每个层次的难度和训练策略都不同。数据泛化是最基本的：同一场景配置下换随机种子（比如红色目标仍在 (1.0, 0.1)，但 seed 从 42 换成 99），测试策略对不同数值扰动的鲁棒性——这只需要训练数据有足够噪声覆盖。场景泛化更难：目标位置组合是训练时没见过的（训练见过 (1.0, 0.0) 和 (0.5, 0.5)，测试给 (0.7, 0.3)），要求策略对任务配置的插值能力——需要训练数据在状态空间均匀采样，而不是聚集在几个固定点。条件泛化最难：物理参数本身变了（质量 +30%、摩擦 -50%），这已经超出状态空间扰动，进入了动力学模型变化的领域——需要域随机化（第 29、31 章）或在线适应。本关的评估设计对应前两个层次：4 个固定测试任务（红/绿/蓝三色导航 + 紧急停止）测场景泛化，9 个专属指标里的 `navigation_success_rate` 和 `collision_rate` 量化泛化效果。工程判断框架：好的系统应该在层次 1、2 上表现良好，在层次 3 上至少不崩溃（安全降级）——本关的 `VLASafetyController` 就是层次 3 的兜底，`soft_pitch_limit` 从 0.1 调到 0.3 会改变安全干预率和成功率的权衡。常见误区是把三个层次混为一谈，用"测试集准确率"一个指标概括所有泛化能力。
<!-- /upkie-qa -->

2. 失败分析的关键是什么？

<!-- upkie-qa:37-q2 -->
关键是找到"第一个可观测信号"——不是最终失败的现象（机器人翻倒、撞上障碍物），而是最早出现的异常指标，因为如果能检测到第一个信号，就能在失败真正发生前触发预防机制。本关的失败模式分类表给出了五种模式及其第一个信号：感知失败的第一个信号是检测结果为空（`detection.visible=0`），此时策略还没开始错误导航，只是原地等待，严重度中等；分布偏移的第一个信号是动作异常大或异常小（策略输出的 `yaw_rate` 或 `forward_velocity` 超出正常范围），此时还没翻倒但已经危险，严重度高；累积误差的第一个信号是轨迹逐渐偏离（停车误差 `mean_stopping_error_m` 持续增大）；执行器饱和的第一个信号是 ctrl 频繁触碰限幅（轮端力矩持续在 ±1.0 N*m 边界）。运行时检测逻辑依赖 `VLASafetyController` 的 `safety_interventions` 计数器：每次安全层介入（限速、俯仰门槛触发、停止逻辑激活）计数器加一，这个计数器的增长速率就是最早的异常信号。面试时的判断框架：先列出所有可能的失败模式，再对每种模式找"最早可观测且与失败有因果关系"的信号，最后设计阈值告警。常见误区是把最终失败现象当成分析对象——翻倒后再分析已经晚了，要分析的是翻倒前 10 步发生了什么。
<!-- /upkie-qa -->

3. OOD 检测的精度和召回率权衡？

<!-- upkie-qa:37-q3 -->
OOD（Out-of-Distribution）检测的阈值设置是一个经典的精度-召回权衡。阈值太高：只有极端异常才触发告警，漏报多——真正的分布外状态（比如目标颜色在训练分布外）不被识别，策略继续运行并可能失败，这是"假阴性"风险。阈值太低：正常波动也触发告警，误报多——系统频繁进入安全模式（本关的 `VLASafetyController` 会清零轮端力矩、停止导航），任务成功率大幅下降，这是"假阳性"风险。本关正文给出的工程实践标准是：设置阈值使误报率 < 5%，即在正常场景下 100 次运行最多触发 5 次误告警。这个 5% 不是随意选的——安全关键系统里，误报率太高会让操作员忽略告警（"狼来了"效应），太低则漏掉真实风险。具体到本关：`soft_pitch_limit` 参数（默认 0.1 rad）就是俯仰角的 OOD 阈值，调到 0.3 会降低误报率（更少的正常晃动触发干预）但增加漏报率（更大的倾斜才被检测到）。面试时的判断框架：先问"误报的代价是什么"（任务中断、操作员疲劳），再问"漏报的代价是什么"（翻倒、碰撞），代价不对称时阈值应该偏向代价高的一侧。常见误区是追求"最优阈值"——实际上阈值需要根据部署场景调整，没有放之四海而皆准的值，关键是建立误报率和漏报率的量化评估流程（本关的 9 个专属指标就是这套流程的起点）。
<!-- /upkie-qa -->

4. 怎样让系统从失败中学习？

<!-- upkie-qa:37-q4 -->
本关正文给出三条路径，对应不同的工程成本和改进效果。第一条是 DAgger（Dataset Aggregation）思路：收集失败 episode 的状态-动作数据，让专家（脚本专家或人类）在这些状态上重新标注正确动作，加入训练集后重新训练 BC 策略——这直接针对分布偏移问题（第 35、36 章的核心理论），因为失败状态正是策略自己会遇到但训练数据里没有的状态。第二条是失败模式分析驱动的针对性数据增强：本关的失败模式分类表（感知失败、分布偏移、累积误差、指令歧义、执行器饱和）告诉你哪类场景覆盖不足，比如如果"蓝色目标导航"失败率高，就增加蓝色目标在不同位置和距离的示范数据（第 35 章的数据覆盖度评估是这套流程的输入）。第三条是改进监控器：把失败分析里找到的"第一个可观测信号"固化成运行时检测规则，让 `safety_interventions` 计数器更早触发，在失败发生前就进入安全模式——这不改进策略本身，但提高了系统整体的安全边际。面试时的判断框架：三条路不是互斥的，优先级通常是"先加监控（成本最低、见效最快）→ 再补数据（中等成本）→ 最后考虑 DAgger 或 RL 微调（成本最高）"。常见误区是只关注策略改进而忽视监控——生产系统里，一个能及时发现失败并安全降级的系统，比一个"平均成功率更高但失败时不可预测"的系统更有价值。
<!-- /upkie-qa -->
