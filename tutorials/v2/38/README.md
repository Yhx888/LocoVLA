## 直觉与概念

<!-- upkie-animation:38-core -->

Eigen 只负责让四维状态向量和点积的维度清晰；它不会替你决定物理语义。真正的接口契约是：`state_error=[m, m/s, rad, rad/s]`，公共力矩是 `N*m`，左、右轮都在各自执行器坐标系输出，且各自被限制在 `[-limit, limit] N*m`。因此“数值一致”要求包含增益顺序、轮轴符号和饱和规则三部分，而不是只比较一个浮点数。

工程部署关注接口、时间、故障和复现。平均能跑不等于最坏情况安全。

本关核心问题是：**如何用可测量证据判断“C++、Eigen 与数值一致性”已经达到岗位可用，而不是只在一次演示中碰巧工作？**

## 教科书级展开

核心关系：

$$
\tau = [2, 0.8, 3, 0.8] dot [e_{x}, e_{v}, e_{\text{pitch}}, e_{\text{pitch},\text{rate}}]
$$

其中 `e_x` 的单位是 m，`e_v` 是 m/s，`e_pitch` 是 rad，`e_pitch_rate` 是 rad/s；增益的单位分别补偿这些量，使最终 `tau` 为 N*m。左轮为 `clip(tau-yaw, -limit, limit)`，右轮为 `clip(-tau-yaw, -limit, limit)`。例如 `e=[0.1, 0.2, -0.05, 0.4]` 时，`tau=2*0.1+0.8*0.2+3*(-0.05)+0.8*0.4=0.53 N*m`。这只适用于当前站立平衡点的小扰动线性反馈；接触丢失或俯仰误差超过课程安全边界时，必须交给上层安全路径，而不能把此线性律外推。

阅读公式或契约时按七层顺序检查：直觉、符号、物理意义、设计动机、逐步推导、数值算例、代码映射。所有物理量使用 SI 单位；离散时间量必须说明采样周期。该关系默认模型字段、坐标方向和执行器语义与 `configs/robot/upkie.json` 一致。

适用范围是当前关卡声明的平衡点、约束和数据分布。接触丢失、传感器过期、动作饱和、输入超出训练分布或公式假设不成立时，必须进入诊断/安全路径，不能继续外推。

数值算例从配置中取一组实际参数，手算一个时间步，再与代码输出逐项对齐。若两者不同，优先检查单位、左右轮方向、平衡点和数组顺序。

## 故障诊断挑战

先区分两类故障：CMake 报 `CMAKE_CXX_COMPILER not set` 是工具链问题，应检查编译器和生成器；批量对照中只有右轮列偏离则是执行器符号或偏航混合问题，应检查 `wheel_torques`。两种故障不能通过提高误差阈值、跳过 CTest 或删除限幅来掩盖。

1. 本关最关键的假设是什么？失效时第一个可观测信号是什么？

<!-- upkie-qa:38-q1 -->
最关键的假设是：四状态线性反馈律 `tau = [2, 0.8, 3, 0.8] · [e_x, e_v, e_pitch, e_pitch_rate]` 只在当前站立平衡点的小扰动范围内有效。正文明确声明"这只适用于当前站立平衡点的小扰动线性反馈；接触丢失或俯仰误差超过课程安全边界时，必须交给上层安全路径，而不能把此线性律外推"。这个假设失效时，第一个可观测信号不是机器人翻倒（那是最终结果），而是俯仰误差 `e_pitch` 持续增大且控制力矩频繁触碰限幅 `[-limit, limit] N*m`——本关故障诊断挑战里描述的"右轮列偏离"就是这类信号在数值对照中的表现。工程上的判断框架：线性反馈的增益是在平衡点线性化得到的，一旦状态偏离平衡点足够远，线性近似误差主导控制精度，此时继续用同一组增益不仅无效，还可能因为力矩方向错误加速失稳。面试时如果被追问"失效了怎么办"，答案是分层安全架构（第 32、34 章）：底层线性律负责小扰动，上层安全监控器检测 `e_pitch` 超阈值后切换到安全路径（停止、蹲下或请求人工干预），两层之间不能有空隙。常见误区是认为"增益调大一点就能覆盖更大范围"——增益越大，线性区外的力矩越激进，反而更容易触发执行器饱和和失稳。
<!-- /upkie-qa -->

2. 为什么当前接口、单位和限幅这样设计？有哪些可替代方案？

<!-- upkie-qa:38-q2 -->
接口设计的核心约束是物理语义清晰和单位一致。状态向量固定为 `[m, m/s, rad, rad/s]` 四个量，增益 `[2, 0.8, 3, 0.8]` 的单位分别补偿这四个量，使点积结果 `tau` 的量纲是 N*m——正文强调"数值一致要求包含增益顺序、轮轴符号和饱和规则三部分，而不是只比较一个浮点数"。左右轮的非对称设计（左轮 `clip(tau-yaw, -limit, limit)`，右轮 `clip(-tau-yaw, -limit, limit)`）来自执行器坐标系方向相反这一机械事实：同一个平衡力矩在左右轮的局部坐标系里符号相反，偏航分量 `yaw` 则同号叠加。限幅 `[-limit, limit]` 保护执行器不超出物理能力，单点算例 `[0.1,0.2,-0.05,0.4]→0.53 N*m` 就是验证这套符号约定的最小测试。可替代方案：一是把左右轮统一到全局坐标系（消除符号不对称，但需要额外的坐标变换层，增加出错点）；二是用速度控制接口代替力矩接口（第 11 章模型契约里轮端已从速度语义改为力矩语义，说明力矩接口是最终选择）；三是把限幅放在上层而不是执行器层（集中管理，但延迟更大）。面试时的判断框架：接口设计没有"最优"，只有"约束下最合理"，关键是能解释每个设计决策的物理依据和失败模式。常见误区是把限幅当成"可有可无的保护"——本关的 1000 组随机对照里，饱和样本和未饱和样本都必须比较误差，因为限幅边界处的数值行为最容易暴露实现差异。
<!-- /upkie-qa -->

4. 如果指标退化 20%，你先查模型、数据、控制还是部署？为什么？

<!-- upkie-qa:38-q4 -->
先查部署（工具链和构建配置），再查控制实现，最后才考虑模型和数据。理由是本关的指标是 Python/C++ 数值对照的最大绝对误差，阈值 `1e-12 N*m` 是机器精度量级——这个指标退化 20%（比如从 1e-13 变成 1e-12 附近）几乎不可能是物理模型或训练数据的问题，最可能的原因是 C++ 侧的编译器优化选项变了（比如从 `-O2` 换成 `-O0` 改变了浮点运算顺序）、Eigen 版本升级改变了点积实现、或者 CMake 生成器切换（Ninja → Visual Studio）引入了不同的浮点精度行为。正文的故障诊断挑战明确区分了两类故障：`CMAKE_CXX_COMPILER not set` 是工具链问题，批量对照中只有右轮列偏离是执行器符号问题——前者影响所有输出，后者只影响特定列，排查顺序应该先看"是否所有列都退化"（工具链）还是"只有某列退化"（符号/混合逻辑）。具体排查步骤：先重跑 `python scripts/run_engineering_lab.py --chapter 38` 确认失败日志里的错误类型，再检查 `outputs/logs/engineering_38.json` 里哪一列误差最大，最后才看控制公式实现。面试时的判断框架：指标退化的排查顺序应该从"最近改了什么"开始，而不是从"最复杂的组件"开始——工程部署阶段的大多数退化来自环境变化，不是算法问题。常见误区是一看到误差变大就去调增益或重新训练，完全忽略了构建环境这个最可能的根因。
